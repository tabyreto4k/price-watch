# 3. ShedLock с JDBC-провайдером для планировщика

- **Статус:** принято
- **Дата:** 2026-07-13
- **Развилка:** Р8 (сводка решений — в [README](../../README.md#архитектурные-решения))

## Контекст

`PriceCheckJob` обходит товары по расписанию и ходит к чужим API. Два одновременных
прогона — двойная нагрузка на источники и дубли уведомлений подписчикам. `@Scheduled` сам
по себе защищает только от повторного запуска внутри одной JVM.

## Решение

`@Scheduled` + `@SchedulerLock(name = "price-check", lockAtMostFor = "PT25M",
lockAtLeastFor = "PT1M")`, провайдер — `JdbcTemplateLockProvider` с `usingDbTime()`.
Таблица `shedlock` заводится миграцией Flyway в той же базе.

## Почему

Postgres в проекте уже есть — блокировка не приносит ни одного нового контейнера.
`usingDbTime()` берёт время из БД, поэтому расхождение часов между инстансами ничего не
ломает. `lockAtMostFor` отпускает лок, если инстанс умер посреди прогона; `lockAtLeastFor`
не даёт двум быстрым прогонам слипнуться при перекрытии деплоя.

Redis ради одной блокировки — лишняя инфраструктура. «У нас один инстанс» ломается первым
же `docker compose up --scale` и первым же перекрытием старого и нового контейнера при
выкате.

## Чем платим

Две грабли, оплаченные на `PriceCheckJobIT`, — обе о том, что тест «джоб ничего не сделал»
обязан отдельно доказывать, что джоб вообще запускался:

- `DELETE` строки из таблицы `shedlock` лок **не** освобождает: `StorageBasedLockProvider`
  помнит в памяти JVM, что строка заведена, и дальше делает только `UPDATE`. Освобождать
  нужно истечением — `lock_until` в прошлое.
- С `usingDbTime()` в колонке лежит время по UTC. Локальный `now()` оказывается впереди, и
  лок точно так же не освобождается: всё, что лезет в эту таблицу мимо ShedLock, обязано
  писать `now() at time zone 'utc'`.

## Когда решение нужно пересмотреть

Если инстансов станет много и появится Redis по другим причинам — провайдер меняется одной
строкой конфигурации, код джоба не трогается.
