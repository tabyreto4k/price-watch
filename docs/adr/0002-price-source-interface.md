# 2. `PriceSource` — единственный интерфейс проекта

- **Статус:** принято
- **Дата:** 2026-07-13
- **Развилка:** Р4 (сводка решений — в [README](../../README.md#архитектурные-решения))

## Контекст

Цена берётся из двух мест разной природы: JSON-эндпоинт карточки Wildberries по артикулу
и произвольная HTML-страница, из которой цену достаёт CSS-селектор. Стандарты проекта
запрещают пары `interface` + единственный `Impl`: абстракция заводится под реальную
вариативность, а не «на будущее».

## Решение

Один интерфейс на проект — `PriceSource` (`supports(input)`, `type()`, `fetch(externalId)`).
Реализации: `WildberriesSource` и `HtmlPageSource`. Больше интерфейсов в проекте нет:
сервисы — классы, DTO — records.

## Почему

Две реализации существуют с первого дня и различаются всем: транспортом (JSON против
HTML), способом разбора, лимитом запросов. `SourceRouter` выбирает источник по вводу
пользователя и больше ничего о них не знает — добавление третьего источника не трогает
ни бота, ни планировщик.

Обратная сторона того же правила: `ProductService`, `SubscriptionService`, `AlertService`
интерфейсов не имеют. Мокать их незачем — юнит-тесты бота мокают классы, а домен
проверяется интеграционными тестами на настоящем Postgres.

## Чем платим

- Общая цепочка ретраев и таймаутов живёт в `SourceHttpClient` рядом с интерфейсом, а не
  в каждой реализации: в двух копиях она разъехалась бы при первой правке.
- `HtmlPageSource` ограничен allow-list доменов с селектором на каждый — новый магазин
  добавляется строкой конфига, но не «любой сайт из коробки».

## Когда решение нужно пересмотреть

Если источник останется один — интерфейс надо убрать, а не оставлять «для симметрии».
