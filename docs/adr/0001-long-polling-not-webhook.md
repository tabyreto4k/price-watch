# 1. Long polling, а не webhook

- **Статус:** принято
- **Дата:** 2026-07-13
- **Развилка:** Р2 (сводка решений — в [README](../../README.md#архитектурные-решения))

## Контекст

Бот должен получать обновления Telegram, работая на VPS за 300–500 ₽/мес. Bot API даёт
два способа: забирать обновления самому (`getUpdates`, long polling) или принимать их
POST-запросами на свой публичный адрес (webhook).

## Решение

Long polling через `telegrambots-springboot-longpolling-starter`.

## Почему

Webhook требует публичный HTTPS-домен с валидным сертификатом и открытый порт: домен,
certbot, автопродление, отдельный nginx. Для бота-уведомлялки это инфраструктура, которая
стоит дороже самой задачи.

Long polling работает из любого NAT: у контейнера вообще нет входящих соединений — в
`compose.prod.yml` наружу не публикуется ни один порт. Деплой сводится к «запусти
контейнер».

## Чем платим

- Задержка доставки — до секунд вместо мгновенной. Для «цена упала» это незаметно.
- Постоянное исходящее соединение и трафик даже в тишине.
- Горизонтально не масштабируется: два инстанса long polling'а на один токен начнут
  отбирать обновления друг у друга. Проверку цен это не задевает — её разводит ShedLock
  ([ADR 3](0003-shedlock-for-scheduler.md)), но второй инстанс бота потребовал бы webhook.

## Когда решение нужно пересмотреть

- Нагрузка вырастет настолько, что понадобится больше одного инстанса.
- Появится домен с сертификатом по другим причинам — тогда webhook почти бесплатен.
- Понадобится serverless-развёртывание: там long polling негде держать.
